# Frontend

The `frontend/` folder contains the Vite React renderer that users see inside the Electron window.

## Files

- `frontend/main.tsx` - React entry point mounted by `index.html`.
- `frontend/components/SettingsDialog.tsx` - The Settings dialog (File → Settings…, Ctrl+,). Manages Claude provider profiles — name, base URL, API key, model(s) for third-party Anthropic-compatible endpoints — with a test-connection button (`claudeProviders.test` runs against the form values, so a key can be verified before it is saved). API keys are write-only from the renderer: list responses carry `hasKey` only, and an empty key field on edit keeps the stored key.
- Agent launcher dropdown - The toolbar's "New terminal" button opens one searchable dropdown (`.launcher-picker`) listing every agent profile plus the saved Claude providers (fetched on open via `claudeProviders.list`, never on the startup path); each provider row launches with the model configured on its profile. Focus lands in the search box on open; typing filters both sections, ArrowUp/ArrowDown move the highlight, Enter launches the highlighted row, and Escape or a click outside closes it. The empty state ("Choose what to spin up.") still renders the profiles as a plain button grid.
- "Open Claude Code" launcher - The `claude-custom` selection kind in `App.tsx`'s launcher profiles: creates a real `kind: "claude"` session carrying `providerProfileId` (the default custom profile, or a specific one picked in the launcher dropdown). With no providers saved, the click opens the Settings dialog with a hint instead of spawning a pane that would fail. The pane runs the **native** `claude` TUI; main injects the profile's `ANTHROPIC_*` env at spawn (`terminal:create`). Model switching after launch uses Claude Code's own `/model` command against the custom endpoint. Custom panes are isolated from the user's global Claude setup: they run with an app-owned `CLAUDE_CONFIG_DIR` (`<userData>/claude-custom-home` — no claude.ai login, no global CLAUDE.md/settings, inherited `ANTHROPIC_*` scrubbed), claude's folder-trust prompt appears once per folder, and their transcripts/resume history live in the app home (thread discovery passes `claudeHome: "custom"`). Subscription "Claude" panes keep the global home.
- Native application menu - `backend/appMenu.cjs` installs File/Edit/View; clicks arrive as `window.vibe.menu.onEvent` actions and are handled in `App.tsx` (new terminal/Claude/Open Claude Code panes, sidebar toggle, open Settings).
- `frontend/App.tsx` - Top-level workspace UI, localStorage persistence, project selection, code-change line totals, session lifecycle, and agent launcher controls. On app reopen, `restoreSession` brings every pane back as a **fresh** terminal (never an auto-resumed chat): a threaded pane's prior thread is moved into `resumeRef` and a new chat is launched, so "restore my workspace" is decoupled from "resume my conversation". `resumeSession` is the explicit opt-in that relaunches the stashed `resumeRef` thread — or, when a chat pane's resume picker (Open Fusion AND Fusion) passes a specific `targetRef`, that saved chat instead (the outgoing conversation becomes the next `resumeRef` either way, and a thread already claimed by another pane is refused).
- Agent launcher availability - `App.tsx` asks `window.vibe.app.getInstalledClis()` once on mount and dims (`.agent-launcher-missing`) any launcher whose CLI the launch-time PATH scan did not find. Dimmed buttons stay **clickable**: panes launch through a login shell whose PATH can be wider than the Electron process's, so a miss is a hint, not a gate. Nothing is dimmed while the probe is still pending (a null report), which avoids flashing every button grey. Terminal and Kimi + CC are never dimmed (no PATH command of their own — Kimi + CC is the vendored binary), and Fusion / Open Fusion follow `claude` / `opencode` since that is what they launch. This replaced an unconditional filter that hid Gemini and Aider from every user, including those who had them installed.
- `frontend/sessionLaunch.ts` - Builds launch/resume commands for Codex, Claude, OpenCode, Cursor, Kimi/Kimi + CC, Qwen, and plain terminal sessions. Claude launches pin `--session-id` but deliberately never pass `--name`: forcing the pane's placeholder label ("Claude 2") onto the session overrides the title Claude generates from the first prompt in its own `/resume` picker. `createThreadRef` mints refs without a title for the same reason — `threadRef.title` only ever holds the provider's own generated/custom title, harvested back from local metadata.
- `frontend/types.ts` - Shared renderer-side domain types for agents, sessions, layouts, thread lookup results, and terminal events.
- `frontend/cwdConflicts.ts` - Pure helpers detecting agent panes that share (or nest inside) one working folder across every scope (Multi + all workspaces), plus the chip label/tooltip formatting. Normalization mirrors `normalizeWorkspacePath` (unconditional lowercase, no symlink resolution — advisory-only impact).
- `frontend/terminalOutput.ts` - React-free PTY byte-stream helpers for `TerminalPane` (2026-08-06, the qwen-pane fixes). `createSyncOutputCoalescer` implements DEC private mode 2026 ("synchronized output") on top of xterm.js, which has no support for it: a full-screen TUI (qwen's virtual viewport wraps **every** repaint in `?2026h`/`?2026l`) paints atomically only if the bracketed frame reaches xterm as one write, but ConPTY re-chunks output at ~4KB, so unheld frames painted partially and the pane flickered/"vibrated" on every repaint tick — worst during qwen's subagent-panel spinner storms. The coalescer holds bytes from BSU to ESU (split markers reassemble across chunk boundaries), passes marker-free streams through untouched, and degrades to passthrough on a per-frame-open deadline (`SYNC_FLUSH_DELAY_MS`) or an oversized frame, so a lost ESU can never wedge a pane. `createSgrMouseTracker` watches the same stream for DECSET 1006 so the wheel handler knows the app speaks SGR mouse encoding.
- `frontend/terminalWheel.ts` - React-free wheel-to-mouse-report math. When a TUI tracks the mouse (qwen does, `?1003h`+`?1006h`), xterm.js reports any DOM wheel event as exactly ONE wheel press however large its delta — and Chromium coalesces a fast flick into a few large-delta events, so qwen's viewport (3 rows per report) moved a single small step and scrolling read as stuck. `computeWheelLines` mirrors xterm `Viewport.getLinesScrolled` (pixel accumulation across sub-line trackpad deltas, line/page modes, a per-event report cap) and `buildSgrWheelReports` emits one SGR wheel report per line, so tracked and untracked panes scroll at the same rate.
- `frontend/electron.d.ts` - Type declarations for the `window.vibe` preload API used by the renderer.
- `frontend/vite-env.d.ts` - Vite environment declarations.
- `frontend/styles.css` - App shell, sidebar, toolbar, terminal pane, status, and tiled-board styling. `:root` carries the design tokens the chrome is built from: colour, a spacing scale (`--space-1..6`), radii, a type scale (`--text-2xs..xl`), motion (`--motion-fast`/`--motion-base`/`--ease-out`), and — load-bearing — the **semantic status colours** (`--status-working`, `--status-done`, `--status-blocked`, `--status-failed`, `--status-idle`). The sidebar dots, the project-card counts, and the pane status pills all read from those, so a state cannot mean one amber in the sidebar and a different one in a pane header, and restyling a state is a token edit rather than a sweep of literals. Motion is reserved for state changes (selection, hover, status) — never a transform on a control the user is aiming at — and `prefers-reduced-motion` is honoured for the spinners and the pane attention pulse. The per-agent accent (`--pane-accent`) identifies a pane through a hairline border and its provider mark rather than a fully saturated outline. The `.oc-skin` block is a deliberate OpenCode-TUI-parity spec and is not restyled beyond mapping its base neutrals onto these tokens.

## Sidebar project cards

Each folder renders as a card — name, middle-truncated path, and a live **working / done / blocked** tally (plus a `failed` chip only when non-zero, since a failed run is finished but not a success). The Multi-mode card carries the same tally over its own sessions. Counts come from `summarizeSessions` in `frontend/attention.ts`, which is composed from `isSessionWorking` and the session's own `attention`/`status`, so a card can never disagree with the pill on the pane it is counting. Buckets are mutually exclusive and evaluated **working → blocked → failed → done**: an open delegation or detached task outranks a settled turn, and a pane blocked on a permission prompt is not "done" even though its turn stopped. `blocked` additionally requires the pane's status **not** to be a latched `done`/`failed` (see *The idle notification* below). The `reconcileStatus` done/failed latch is what separates a real block from a finished one — an interrupt leaves status `waiting`, a finished turn leaves it `done`. A scope with nothing happening falls back to a plain terminal count rather than a row of zeros.

This needs no new state, IPC, or polling: every workspace's sessions are already in renderer state at the sidebar render site and keep receiving live updates while their folder is in the background (all mutations flow through `updateAnySession`, and the terminal/chat event subscriptions are mounted once with `[]` deps). One honest limitation: panes only mount for the **active** scope, so sessions restored from localStorage in a folder the user has not opened this launch have no process yet (`restoreSession` forces them back to `idle`) and count toward the total only, until the folder is visited.

### The idle notification

claude fires its idle `Notification` hook (matcher `idle_prompt` → `agent.waiting` / reason `question`, `backend/agentTelemetry.cjs`) roughly a minute after **every** turn ends, on any pane left sitting at its prompt. That is the same attention shape an interrupt produces, so it used to land on a finished pane and make the card read **blocked** while the pane's own pill still read `done`, and re-raise an attention dot the user had already dismissed.

The rule is now applied once at the write site: in `applyAcceptedAgentAttention` **a settled turn owns its attention** — while status is a latched `done`/`failed`, an incoming `waiting` does not overwrite the completion or its `unread` flag. Three things are deliberately *outside* that guard:

- the **delegation bracket release** (`waiting`/`question` clears `subagentDepth`) still applies — the bracket expiry is a fact about the delegation, not a notification;
- a late `completed`/`failed` still writes, since it describes the same settled turn;
- while the pane is `running`/`starting`/`idle` the event applies normally, which preserves it as the ~60s **liveness backstop** for a turn whose `Stop` hook never landed.

Mid-turn approval waits are untouched: a permission prompt can only happen inside a turn, and that turn's `UserPromptSubmit` → `applyAgentRunning(turnStart)` has already bypassed the latch. `summarizeSessions` keeps the same settled check as a second line of defence, because `applyTerminalAttention`, `applyFusionAttention` and `restoreSession` write attention without going through that path.

These hooks reach **terminal panes only**. They live in an app-owned `claude-settings.json` that the PTY shim injects with `--settings` when it resolves a `claude` on the pane's shimmed PATH (vibeTerminal never writes the user's `~/.claude/settings.json`). The Fusion planner is spawned by the singleton `fusionChatHost.cjs` with its *own* `--settings` file, which carries planner/executor metadata and no `hooks` key; that host also has no per-pane `VIBE_TERMINAL_SESSION_ID`/callback env for a notify program to POST with. So a chat pane's `waiting` is always a genuine block (`needs_decision`/`ask_human`, or an OpenCode `permission.asked`), never an idle nag.

`restoreSession` also drops a persisted `waiting` attention (and clears attention outright for panes that auto-start), and clears `unread` on any attention that does survive — after a relaunch there is no unseen notification. Restore always hands a started pane a **fresh** terminal, so a stored `waiting` describes an approval/question prompt that died with the previous process; keeping it made every project that had ever parked a pane at its idle prompt — claude's `idle_prompt` Notification hook fires on any pane left sitting there — open as **blocked** on the next launch. A paused pane whose process really did exit keeps its `completed`/`failed` attention, which still matches the `status` restored beside it.

## Components

- `frontend/components/TerminalPane.tsx` - Owns the xterm instance for a session (pinned to the session id so it survives launch-command changes), sends terminal input/resize IPC calls, receives PTY events, relaunches the PTY only on a launchToken bump, and polls for agent thread metadata. The PTY size handshake is fit-gated (2026-07-19): `create()` advertises cols/rows only after a fit has measured real pane bounds — shipping xterm's 80x24 pre-fit default used to resize a live PTY down to it on the backend's remount dedup path, so a full-screen TUI (kimi, claude) repainted for the wrong width and shredded the pane — and a live-session snapshot replay clears the sent-size memo and re-fits so PTY and xterm always reconverge (the backend dedups an equal-size resize). ## Split tiles

One board tile can hold several terminals as a nested split, all visible at once. The model is two optional fields on `AgentSession`, so a tile with one member stores neither and is byte-identical to the pre-split behaviour (no migration, no schema bump — `restoreSession`'s `...session` spread already round-trips a nested object):

- **`tileId`** names the tile's **anchor** (a session with `tileId === id`). `effectiveTileId(s) = s.tileId ?? s.id`.
- **`splitTree`** lives only on the anchor: a binary tree of `{dir, ratio, a, b}` branches over `{id}` leaves. The partition is structural — no holes or overlaps are representable — and a divider drag changes exactly one number.

The tile's board geometry is the anchor's `layout`; a non-anchor member keeps its own `layout` as dead data so popping it back out has a box to restore (`findNextFluidLayout` filters to anchors so that dead data never reserves space). `persistLayout` needs no change: every id TiledBoard commits is an anchor session id.

Grouping lives on the session because it has nowhere else to go — `restoreStoredWorkspace` reconstructs only `{id, name, path, sessions}` and discards any other workspace-level key, and Multi mode has no container object at all. `restoreSession` therefore does **shape** validation only, and `reconcileTiles` runs wherever sessions become a *set* (`restoreStoredWorkspace`, `loadMultiSessions`) to repair membership: stray trees on non-anchors, leaves naming missing sessions, orphaned `tileId`s, one-member tiles, an anchor missing from its own tree, and two tiles claiming one session. It is idempotent and **never drops a session** — anything unplaceable reappears as an ordinary solo tile.

Splitting is a pane-header action (Split right / Split down); closing a sub-pane is the primary un-split (the tile collapses into its sibling, re-anchoring if the anchor left, and at one member dissolves entirely with the survivor inheriting the board box), and a grouped pane also gets **Pop out of tile**, which needs a fresh `findNextFluidLayout` box because its stored one is the tile's. Maximize acts on the **tile**, not the sub-pane: maximizing one terminal of a split would hide its siblings, and a hidden pane has a zero-sized box that `fitAndResize` refuses to measure, so it could never advertise a real PTY size. Two mounting hazards follow from several panes sharing one frame and are handled in `TerminalPane`: `terminal.focus()` at construction is gated on an `autoFocus` prop (`session.id === selectedSessionId`) so the last-rendered pane cannot steal focus, and the launch-time `.pane-frame` transition suppression is refcounted through a `WeakMap` so one forced synchronous layout happens per frame per commit instead of one per pane.

## Working / done signals

Two sidebar signals share the dot slot on each folder button and the Multi-mode card (`App.tsx`), with the blue attention dot taking priority over the working spinner:

- **Blue attention dot** (`shouldShowAttentionDot`) - a pane finished a turn / needs you (`attention.unread` + `waiting|completed|failed`). Cleared by selecting the pane.
- **Amber working spinner** (`.attention-dot-working`, gated by `isSessionWorking`) - a pane is actively running a foreground turn (`status === "running"`), still owns at least one in-flight detached Fusion / Open Fusion task (`detachedTaskIds`), or has at least one open subagent delegation (`subagentDepth`).

When a planner launches detached work, its foreground launcher turn still settles to `done`, but that result stays read while any detached task id remains, so it cannot latch a blue done dot over the spinner. The host's settled event removes the id, then wakes the planner with the task report as a fresh turn; that wake-report turn's result produces the real done dot normally.

Terminal agent panes get the same guarantee from a weaker signal. `subagentDepth` counts **delegation brackets** — `agent.subagent.started`/`.stopped`, emitted from a tool-call boundary the model itself created (claude `PreToolUse`/`PostToolUse` with `matcher: "Task"`; kimi-custom and qwen native `SubagentStart`/`SubagentStop`; stock kimi `PreToolUse`/`PostToolUse` matching `^Agent$`; codex's subagent-tagged child tool hooks). It is a count rather than an id set because no provider matcher can carry a task id and the notify transport is argv-only, which is why it has explicit expiry rules (below). While the bracket is open, a provider completion is **suppressed outright** rather than settled-with-the-dot-hidden: kimi and kimi-custom fire the session-level `Stop` hook at a *child's* turn end (subagents share the session's hook engine), so on the wire the pane's own turn end is indistinguishable from a subagent's, and writing `done` from it is exactly the bug. The event carries no id, so it can never be re-attributed later — deferring and replaying it would just reproduce the bug one event later. `waiting` is never suppressed (a child asking for permission is a real user-facing wait, and `waiting` is not latched), and a process exit (`source: "shim"`) is never suppressed. Net effect for a genuinely detached subagent: spinner stays amber with no blue dot, the pill holds `running` and then drops to `waiting` after the long quiet window (status only — no unread attention), and the real `done` + dot arrives with the wake turn's own `Stop`.

"Working" must mean the agent is working, not the user interacting, so `status === "running"` is set by exactly one source per pane kind — never by raw output that could be a keystroke echo or a focus/click redraw:

- **claude / opencode / cursor / kimi / kimi-custom / qwen** (`isTurnTelemetryKind`) - driven purely by turn telemetry: the `agent-running` event with `turnStart:true` (a genuine turn start) forces `running` via `applyAgentRunning` even past the done/failed latch; `turnStart:false` (claude tool activity) goes through `reconcileStatus`, so a tool hook whose POST races past the turn's `Stop` cannot resurrect a finished pane. `agent-attention` settles status to `waiting`/`done`. `TerminalPane` never marks these working from output, and `applyTerminalStatus` ignores a `running` derived from their terminal events. (cursor's turn start is its `beforeSubmitPrompt` hook; it emits no `waiting`, so `running` simply holds until `stop`. kimi's is the config.toml `UserPromptSubmit` hook vibeTerminal merges in, with claude-parity events including `PermissionRequest` approval waits; kimi-custom shares that channel — same hook set, merged into the same shared config.toml under its own marker. qwen's is the same claude-parity hook set merged into `$QWEN_HOME`/`~/.qwen` `settings.json`, name-tagged `vibeterminal-notify`.) These kinds also carry the **delegation bracket**: a bracketed `agent.completed`/`agent.failed` is dropped (see above), and `agent.subagent.started` is the *second* signal allowed to override a finished pill.
- **codex** - App-owned lifecycle state survives pane unmounts. A trusted passive Codex `UserPromptSubmit` observer reports the provider thread/turn id and forces `running`; bare Enter is the compatibility fallback until that observer is trusted or on older Codex. Approval/tool observers report waiting/running without changing Codex decisions. The global PTY listener refreshes only an already-started turn's 60s safety watchdog (with the same 450ms input-echo grace), so workspace switches/maximize do not lose working state; watchdog waiting self-heals if later output resumes. Esc/Ctrl+C settles to waiting. Legacy completion is accepted only when its provider thread id matches the pane's discovered root and, when known, its turn id matches the active turn; early completion waits for root discovery, child-agent and stale-turn completions are dropped. With no bound turn id, a completion is additionally rejected once the pane has already settled a turn (`codexTurnLive === false`) — an unobserved turn (`undefined`) still accepts, since that is the older/untrusted-codex compatibility path. Subagent-tagged observer payloads never report `running`/`waiting`; they are narrowed to the delegation bracket, so a parent completion landing while a child tool call is open is dropped. Codex's bracket spans individual child tool calls only — codex exposes no whole-delegation terminator, so a completion landing *between* two child tool calls is still accepted. Codex is also excluded from the latch bypass below, since its bracket can legitimately trail a settled root turn.
- **plain terminals / others** - the mounted `TerminalPane` output heuristic (`markActiveFromOutput`): output reads as "working" unless it lands within `INPUT_GRACE_MS` of the user's last keystroke/click. On unmount, a heuristic `running` state settles to `waiting`; background non-agent output does not produce a spinner by design.

The done/failed pill is a latch (`reconcileStatus`): trailing output — the shell prompt returning after an agent exits, a stray byte — must never flip a finished pane back to working/waiting. Two things release it. The first is a **subagent delegation start** (`agent.subagent.started`, telemetry kinds only — codex is excluded): it is emitted from a tool-call boundary the model itself created, so unlike raw output it can never be a keystroke echo, a focus/mouse report, a TUI redraw or a replayed snapshot, and it is an onset rather than a completion (`agent.subagent.stopped` stays latch-respecting). It is necessary as well as safe: kimi delivers a detached subagent's result as a synthetic user-role message that fires no `UserPromptSubmit`, so without this rule the only release would be the human typing. The second is **keyboard input** into the pane (`statusAfterUserInput` in `attention.ts`, applied through the pane's `onInputStatusRelease` callback which bypasses `reconcileStatus`):

- **codex / plain terminals** - human typing releases a latched prior result. For Codex, bare Enter additionally starts the App-owned fallback turn state; trusted provider lifecycle telemetry supersedes that approximation. Plain terminals still wait for real output before becoming running.
- **claude / kimi / kimi-custom / qwen (approval waits only)** - answering a permission prompt has no hook of its own (`PreToolUse` fires before the prompt, `PostToolUse` only when the tool ends), so the answer keystroke flips `waiting`->`running` immediately instead of reading "requires feedback" for the whole tool run. Idle/question waits stay put — composing a prompt is not working.
- **telemetry kinds, bare Esc while `running`** - the TUI interrupt key. No hook fires for an interrupt (claude's `Stop` does not), so Esc settles the pill to `waiting` immediately; if it merely dismissed a menu, the next telemetry event re-asserts `running` (waiting->running is never latched).
- `isHumanTerminalInput` filters out terminal-generated reports (focus in/out, mouse reports, arrow keys — anything starting with a bare ESC except a bracketed paste), so clicking or focusing a finished TUI pane never disturbs its pill.

Two more guards keep pills truthful across missed hooks and remounts:

- **Stale-running watchdog** (`TELEMETRY_RUNNING_QUIET_MS`, `armTelemetrySettle` in `TerminalPane`): a telemetry-kind pane that stays `running` with zero PTY output for ~12s settles to `waiting` — these TUIs repaint their spinner constantly while genuinely working, so prolonged total silence means the turn ended without its hook (interrupt, lost POST). The settle fires only if the status is unchanged since arming, so a `starting`->`running` transition never settles a fresh turn on the shorter boot delay. While a delegation bracket is open the window widens to `TELEMETRY_DELEGATION_QUIET_MS` (~120s), because a delegating pane is *expected* to be quiet — the parent idles at a static prompt while its subagent works. That long window doubles as the bracket's absolute expiry (`onDelegationTimeout`), so a lost close event cannot wedge a pane "working" forever. The delay is fixed at arm time, so the pane re-arms whenever `subagentDepth` changes — that both rescues a delegation opened mid-quiet-stretch and drops an ordinary turn straight back to the 12s window. The bracket's other releases: a genuine turn start, a bare Esc, a process exit/error, any relaunch/restore path, and an accepted idle-prompt `waiting` (`reason: "question"`, which covers a *denied* claude Task — `PreToolUse` fires but `PostToolUse` never does). An `approval` wait deliberately does **not** release it: that is a child asking permission mid-delegation.
- **Codex watchdog** (`CODEX_RUNNING_QUIET_MS` in `App.tsx`): an App-owned 60s zero-output safety net catches menu Enter false starts or a lost completion POST without tying lifetime to a mounted pane. A timeout is provisional; later PTY activity reasserts running and re-arms it.
- **Remounts are replays**: a `snapshot` is buffered old output (workspace switch, maximize), so it never marks a pane working (`statusFromTerminalEvent` returns null for a running snapshot; the pane only re-arms the telemetry settle from it), and the launch effect only sets `starting` when the status is `idle` — every genuine launch path (create/restart/resume/settings change) resets to `idle` first, so a remount of a live pane never disturbs a settled `done`/`failed`/`waiting` pill. The reattach arm inherits the long delegation window too, so a live-but-quiet delegating pane is no longer settled to `waiting` 12s after a workspace switch back.

The Fusion / Open Fusion chat panes' header pill takes its live states (working/waiting/failed) from the pane's local flags, but its settled state from the app-reconciled `session.status` — the same source the sidebar reads: `done` after a completed turn, `waiting` after an interrupt (the pane is blocked on the user, not finished), `failed` when the last turn errored. Only a pane with nothing settled reads "ready". Before this, everything non-busy collapsed into "ready", so a pane that was just waiting for input was indistinguishable from one that had finished a task.

Two rules keep the chat panes' `done` from becoming a permanent state (2026-07-04):

- **Chat-pane reattach replays are status/attention-neutral.** When a chat pane remounts onto a live host session (project switch back), the host re-emits its buffered history tagged `replay: true` (`fusionChatHost.cjs` / `openFusionChatHost.cjs` `replaySession`). Replayed events rebuild the pane's transcript and local flags only: the pane's `reportStatus`/`reportAttention` wrappers drop app-level emission for them, both App lifecycle mirrors (`applyFusionChatLifecycle` / `applyOpenFusionChatLifecycle`) skip replayed status/attention events, and `main.cjs` doesn't re-forward replayed `background-activity`. The one App-level replay exception is `background-task` started/settled history: its idempotent task-id reducer rehydrates whether detached work is still live without touching status or attention. The panes' launch effect also only emits `starting` when the status is `idle`/`starting` — same rule as `TerminalPane`'s remount guard above. Before this, every project switch re-latched `done` and re-lit the blue attention dot the user had already acknowledged, so a finished chat pane could never settle back to "ready".
- **A settled `done` is a notification, not a resting state.** Engaging the pane again — clicking it (the same gesture that clears the unread dot via `selectSession`) or typing the next prompt into the composer — acknowledges the finished turn (`acknowledgeCompletedTurn`) and releases the pill `done` -> `idle` ("ready"). `waiting`/`failed` stay put: they still need an answer / carry the error until the next turn starts.

## Shared-folder chip

Every agent pane (plain shells excluded) whose folder overlaps another agent pane's — same folder or nested, across Multi and all workspaces — shows a neutral `×N here` chip in its header (`pane-cwd-conflict-chip`, computed by `frontend/cwdConflicts.ts` in `App.tsx` and passed to all three pane components). Neutral by design: side-by-side agents on one project is normal use, not a mistake. The chip tints amber as `×N active` only while this pane AND an overlapping peer are both mid-turn (`running`/`starting`) — the real collision window, since the harnesses' stale-write checks don't coordinate across processes. The tooltip names the other panes and their scope.
