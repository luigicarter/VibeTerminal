# Frontend

The `frontend/` folder contains the Vite React renderer that users see inside the Electron window. Standalone session observations are backend-owned; see [terminal runtime and board behavior](terminal-runtime.md) for the current identity, progress, title, and placement contracts.

## Files

- `frontend/main.tsx` - React entry point mounted by `index.html`.
- `frontend/components/WorkspaceStart.tsx` + `workspaceStart.css` - Balanced session catalog and initial project actions; uses the same profile registry and launch callbacks as the toolbar.
- `frontend/components/OrchestratorPanel.tsx` + `workspaceDockResize.ts` + `workspaceDock.css` - Workspace tool dock with pointer/keyboard resizing, persisted height and viewport clamps; full retained transcript scrolling follows new messages only while at the bottom.
- `frontend/components/SettingsDialog.tsx` - The Settings dialog (File → Settings…, Ctrl+,). Manages Claude provider profiles — name, base URL, API key, model(s) for third-party Anthropic-compatible endpoints — with a test-connection button (`claudeProviders.test` runs against the form values, so a key can be verified before it is saved). API keys are write-only from the renderer: list responses carry `hasKey` only, and an empty key field on edit keeps the stored key.
- Agent launcher dropdown - The toolbar's "New session" button opens one searchable dropdown (`.launcher-picker`) listing every agent profile plus the saved Claude providers (fetched on open via `claudeProviders.list`, never on the startup path); each provider row launches with the model configured on its profile. Focus lands in the search box on open; typing filters both sections, ArrowUp/ArrowDown move the highlight, Enter launches the highlighted row, and Escape or a click outside closes it. The empty session board uses `WorkspaceStart.tsx`: every profile appears in an equally sized launch card with a direct label, description and availability hint. Without a project, it offers Open project, New project and Multi mode.
- "Open Claude Code" launcher - The `claude-custom` selection kind in `App.tsx`'s launcher profiles: creates a real `kind: "claude"` session carrying `providerProfileId` (the default custom profile, or a specific one picked in the launcher dropdown). With no providers saved, the click opens the Settings dialog with a hint instead of spawning a pane that would fail. The pane runs the **native** `claude` TUI; main injects the profile's `ANTHROPIC_*` env at spawn (`terminal:create`). Model switching after launch uses Claude Code's own `/model` command against the custom endpoint. Custom panes are isolated from the user's global Claude setup: they run with an app-owned `CLAUDE_CONFIG_DIR` (`<userData>/claude-custom-home` — no claude.ai login, no global CLAUDE.md/settings, inherited `ANTHROPIC_*` scrubbed), claude's folder-trust prompt appears once per folder, and their transcripts/resume history live in the app home (thread discovery passes `claudeHome: "custom"`). Subscription "Claude" panes keep the global home.
- Native application menu - `backend/appMenu.cjs` installs File/Edit/View; clicks arrive as `window.vibe.menu.onEvent` actions and are handled in `App.tsx` (new terminal/Claude/Open Claude Code panes, sidebar toggle, open Settings).
- `frontend/App.tsx` - Top-level workspace UI, localStorage persistence, project selection, code-change line totals, session lifecycle, and agent launcher controls. On app reopen, `restoreSession` brings every pane back as a **fresh** terminal (never an auto-resumed chat): a threaded pane's prior thread is moved into `resumeRef` and a new chat is launched, so "restore my workspace" is decoupled from "resume my conversation". `resumeSession` is the explicit opt-in that relaunches the stashed `resumeRef` thread — or, when a chat pane's resume picker (Open Fusion AND Fusion) passes a specific `targetRef`, that saved chat instead (the outgoing conversation becomes the next `resumeRef` either way, and a thread already claimed by another pane is refused).
- Agent launcher availability - `App.tsx` asks `window.vibe.app.getInstalledClis()` once on mount and dims (`.agent-launcher-missing`) any launcher whose CLI the launch-time PATH scan did not find. Dimmed buttons stay **clickable**: panes launch through a login shell whose PATH can be wider than the Electron process's, so a miss is a hint, not a gate. Nothing is dimmed while the probe is still pending (a null report), which avoids flashing every button grey. Terminal and Kimi + CC are never dimmed (no PATH command of their own — Kimi + CC is the vendored binary), and Fusion / Open Fusion follow `claude` / `opencode` since that is what they launch. The shared provider capability registry controls supported CLIs. Aider has been removed; saved Aider panes become paused plain terminals.
- `frontend/sessionLaunch.ts` - Builds launch/resume commands for Codex, Claude, OpenCode, Cursor, Kimi/Kimi + CC, Qwen, and plain terminal sessions. Claude launches pin `--session-id` but deliberately never pass `--name`: forcing the pane's placeholder label ("Claude 2") onto the session overrides the title Claude generates from the first prompt in its own `/resume` picker. `createThreadRef` mints refs without a title for the same reason — `threadRef.title` only ever holds the provider's own generated/custom title, harvested back from local metadata.
- `frontend/types.ts` - Shared renderer-side domain types for agents, sessions, layouts, thread lookup results, and terminal events.
- `frontend/cwdConflicts.ts` - Pure helpers detecting agent panes that share (or nest inside) one working folder across every scope (Multi + all workspaces), plus the chip label/tooltip formatting. Normalization mirrors `normalizeWorkspacePath` (unconditional lowercase, no symlink resolution — advisory-only impact).
- `frontend/terminalOutput.ts` - React-free PTY byte-stream helpers for `TerminalPane` (2026-08-06, the qwen-pane fixes). `createSyncOutputCoalescer` implements DEC private mode 2026 ("synchronized output") on top of xterm.js, which has no support for it: a full-screen TUI (qwen's virtual viewport wraps **every** repaint in `?2026h`/`?2026l`) paints atomically only if the bracketed frame reaches xterm as one write, but ConPTY re-chunks output at ~4KB, so unheld frames painted partially and the pane flickered/"vibrated" on every repaint tick — worst during qwen's subagent-panel spinner storms. The coalescer holds bytes from BSU to ESU (split markers reassemble across chunk boundaries), passes marker-free streams through untouched, and degrades to passthrough on a per-frame-open deadline (`SYNC_FLUSH_DELAY_MS`) or an oversized frame, so a lost ESU can never wedge a pane. `createSgrMouseTracker` watches the same stream for DECSET 1006 so the wheel handler knows the app speaks SGR mouse encoding.
- `frontend/terminalWheel.ts` - React-free wheel-to-mouse-report math. When a TUI tracks the mouse (qwen does, `?1003h`+`?1006h`), xterm.js reports any DOM wheel event as exactly ONE wheel press however large its delta — and Chromium coalesces a fast flick into a few large-delta events, so qwen's viewport (3 rows per report) moved a single small step and scrolling read as stuck. `computeWheelLines` mirrors xterm `Viewport.getLinesScrolled` (pixel accumulation across sub-line trackpad deltas, line/page modes, a per-event report cap) and `buildSgrWheelReports` emits one SGR wheel report per line, so tracked and untracked panes scroll at the same rate.
- `frontend/electron.d.ts` - Type declarations for the `window.vibe` preload API used by the renderer.
- `frontend/vite-env.d.ts` - Vite environment declarations.
- `frontend/styles.css` - App shell, sidebar, toolbar, terminal pane, status, and tiled-board styling. `:root` carries the design tokens the chrome is built from: colour, a spacing scale (`--space-1..6`), radii, a type scale (`--text-2xs..xl`), motion (`--motion-fast`/`--motion-base`/`--ease-out`), and — load-bearing — the **semantic status colours** (`--status-working`, `--status-done`, `--status-blocked`, `--status-failed`, `--status-idle`). The sidebar dots, the project-card counts, and the pane status pills all read from those, so a state cannot mean one amber in the sidebar and a different one in a pane header, and restyling a state is a token edit rather than a sweep of literals. Motion is reserved for state changes (selection, hover, status) — never a transform on a control the user is aiming at — and `prefers-reduced-motion` is honoured for the spinners and the pane attention pulse. The per-agent accent (`--pane-accent`) identifies a pane through a hairline border and its provider mark rather than a fully saturated outline. The `.oc-skin` block is a deliberate OpenCode-TUI-parity spec and is not restyled beyond mapping its base neutrals onto these tokens.

## Sidebar project cards

Each folder renders as a card — name, middle-truncated path, and a live **working / done / blocked** tally (plus a `failed` chip only when non-zero, since a failed run is finished but not a success). The Multi-mode card carries the same tally over its own sessions. Counts come from `summarizeSessions` in `frontend/attention.ts`, which is composed from `isSessionWorking` and the session's own `attention`/`status`, so a card can never disagree with the pill on the pane it is counting. Buckets are mutually exclusive and evaluated **working → blocked → failed → done**: an open delegation or detached task outranks a settled turn, and a pane blocked on a permission prompt is not "done" even though its turn stopped. `blocked` additionally requires the pane's status **not** to be a latched `done`/`failed` (see *The idle notification* below). The `reconcileStatus` done/failed latch is what separates a real block from a finished one — an interrupt leaves status `waiting`, a finished turn leaves it `done`. A scope with nothing happening falls back to a plain terminal count rather than a row of zeros.

This needs no new state, IPC, or polling: every workspace's sessions are already in renderer state at the sidebar render site and keep receiving live updates while their folder is in the background (all mutations flow through `updateAnySession`, and the terminal/chat event subscriptions are mounted once with `[]` deps). One honest limitation: panes only mount for the **active** scope, so sessions restored from localStorage in a folder the user has not opened this launch have no process yet (`restoreSession` forces them back to `idle`) and count toward the total only, until the folder is visited.

### The idle notification

claude fires its idle `Notification` hook (matcher `idle_prompt` → `agent.waiting` / reason `question`, `backend/agentTelemetry.cjs`) roughly a minute after **every** turn ends, on any pane left sitting at its prompt. That is the same attention shape an interrupt produces, so it used to land on a finished pane and make the card read **blocked** while the pane's own pill still read `done`, and re-raise an attention dot the user had already dismissed.

The rule is now applied once at the write site: in `applyAcceptedAgentAttention` **a settled turn owns its attention** — while status is a latched `done`/`failed`, an incoming `waiting` does not overwrite the completion or its `unread` flag. Three things are deliberately *outside* that guard:

- the **delegation bracket release** (`waiting`/`question` clears `subagentDepth`) still applies — the bracket expiry is a fact about the delegation, not a notification;
- a late `completed`/`failed` still writes, since it describes the same settled turn;
- while the pane is `running`/`starting`/`idle` the event applies normally, which preserves it as the ~60s **liveness backstop** for a turn whose `Stop` hook never landed.

Mid-turn approval waits are untouched: a permission prompt can only happen inside a turn, and that turn's `UserPromptSubmit` → `applyAgentRunning(turnStart)` has already bypassed the latch. `summarizeSessions` keeps the same settled check as a second line of defence, because `applyTerminalAttention`, `applyFusionAttention` and `restoreSession` write attention without going through that path.

These hooks reach **terminal panes only**. They live in an app-owned `claude-settings.json` that the PTY shim injects with `--settings` when it resolves a `claude` on the pane's shimmed PATH (vibeTerminal never writes the user's `~/.claude/settings.json`). The Fusion planner is spawned by the singleton `fusionChatHost.cjs` with its *own* `--settings` file, which carries planner/executor metadata and no `hooks` key; that host also has no per-pane `VIBE_TERMINAL_SESSION_ID`/callback env for a notify program to POST with. So a chat pane's `waiting` is always a genuine block (`needs_decision`/`ask_human`, or an OpenCode `permission.asked`), never an idle nag.

`restoreSession` also drops a persisted `waiting` attention (and clears attention outright for panes that auto-start), and clears `unread` on any attention that does survive — after a relaunch there is no unseen notification. Restore always hands a started pane a **fresh** terminal, so a stored `waiting` describes an approval/question prompt that died with the previous process; keeping it made every project that had ever parked a pane at its idle prompt — claude's `idle_prompt` Notification hook fires on any pane left sitting there — open as **blocked** on the next launch. A paused pane whose process really did exit keeps its `completed`/`failed` attention, which still matches the `status` restored beside it.

## Split tiles

One board tile can hold several terminals as a nested split, all visible at once. The model is two optional fields on `AgentSession`, so a tile with one member stores neither and is byte-identical to the pre-split behaviour (no migration, no schema bump — `restoreSession`'s `...session` spread already round-trips a nested object):

- **`tileId`** names the tile's **anchor** (a session with `tileId === id`). `effectiveTileId(s) = s.tileId ?? s.id`.
- **`splitTree`** lives only on the anchor: a binary tree of `{dir, ratio, a, b}` branches over `{id}` leaves. The partition is structural — no holes or overlaps are representable — and a divider drag changes exactly one number.

The tile's board geometry is the anchor's `layout`; a non-anchor member keeps its own `layout` as dead data so popping it back out has a box to restore (`findNextFluidLayout` filters to anchors so that dead data never reserves space). `persistLayout` needs no change: every id TiledBoard commits is an anchor session id.

Grouping lives on the session because it has nowhere else to go — `restoreStoredWorkspace` reconstructs only `{id, name, path, sessions}` and discards any other workspace-level key, and Multi mode has no container object at all. `restoreSession` therefore does **shape** validation only, and `reconcileTiles` runs wherever sessions become a *set* (`restoreStoredWorkspace`, `loadMultiSessions`) to repair membership: stray trees on non-anchors, leaves naming missing sessions, orphaned `tileId`s, one-member tiles, an anchor missing from its own tree, and two tiles claiming one session. It is idempotent and **never drops a session** — anything unplaceable reappears as an ordinary solo tile.

Splitting is a pane-header action (Split right / Split down); closing a sub-pane is the primary un-split (the tile collapses into its sibling, re-anchoring if the anchor left, and at one member dissolves entirely with the survivor inheriting the board box), and a grouped pane also gets **Pop out of tile**, which needs a fresh `findNextFluidLayout` box because its stored one is the tile's. Maximize acts on the **tile**, not the sub-pane: maximizing one terminal of a split would hide its siblings, and a hidden pane has a zero-sized box that `fitAndResize` refuses to measure, so it could never advertise a real PTY size. Two mounting hazards follow from several panes sharing one frame and are handled in `TerminalPane`: `terminal.focus()` at construction is gated on an `autoFocus` prop (`session.id === selectedSessionId`) so the last-rendered pane cannot steal focus, and the launch-time `.pane-frame` transition suppression is refcounted through a `WeakMap` so one forced synchronous layout happens per frame per commit instead of one per pane.

## Working / done signals

Standalone panes, sidebar counts, conflict chips, and unread dots use the same runtime projection. The App subscribes before reading retained snapshots, rejects old generations/revisions, and persists confirmed conversation references separately from live observation. Approval attention disappears when observed activity resumes; completion attention waits for child work to finish. Agent exit and shell exit are distinct from turn completion. Unknown/provisional observation remains neutral rather than guessing from output or elapsed silence.

Fusion and Open Fusion keep their existing chat event reducers, review gates, detached-task records, and replay-neutral unread behavior. Their `fusion`/`openFusion` flags determine this routing; provider kind alone does not.

See [terminal runtime](terminal-runtime.md) for the full lifecycle and provider capability contracts.

## Shared-folder chip

Every agent pane (plain shells excluded) whose folder overlaps another agent pane's — same folder or nested, across Multi and all workspaces — shows a neutral `×N here` chip in its header (`pane-cwd-conflict-chip`, computed by `frontend/cwdConflicts.ts` in `App.tsx` and passed to all three pane components). Neutral by design: side-by-side agents on one project is normal use, not a mistake. The chip tints amber as `×N active` only while this pane AND an overlapping peer are both mid-turn (`running`/`starting`) — the real collision window, since the harnesses' stale-write checks don't coordinate across processes. The tooltip names the other panes and their scope.

## Entry Points

- `index.html` loads `/frontend/main.tsx`.
- `tsconfig.json` includes `frontend/` for strict renderer typechecking.
- `npm run dev:frontend` starts the Vite renderer on `127.0.0.1:5173`.
