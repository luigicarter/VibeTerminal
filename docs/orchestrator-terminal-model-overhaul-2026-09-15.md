# Orchestrator overhaul: one terminal model (2026-09-15)

The question the user asked after eighteen ladder rounds: is the fix-by-fix path the right one, or does the Orchestrator need a new representation of the terminals it navigates? This document answers it from the records: what the user's sentences need, what the system is today, and what a complete overhaul would replace, delete and keep. It is a plan, not an implementation. The completion ladder (`docs/orchestrator-completion-ladder-2026-09-14.md`) is its acceptance test.

## 1. The verdict in one paragraph

The ladder's eighteen rounds fixed seventeen defects and took Luna from 4 to 33 of 35 sentences. Of those defects, thirteen were the same defect in different clothes: the app holds several partial pictures of "which pane does this sentence mean" and they disagree. "The pane Lina last typed into" is computed four ways from two stores. The selector in a sentence is extracted four times per request. Seven vocabularies describe what a pane is doing. Five functions decide what a pane is called. Each fix aligned two of these; the next sentence found a third. The remaining variance between runs is now the Brain's own single-call guess on two or three sentences, which a stable representation would take out of its hands. The overhaul is therefore not a better Brain or a faster one: it is one terminal model that the user, the Brain and the app all read, with reference resolution done once, in code, before any model is asked.

## 2. What the sentences need

The 128 saved utterances (`scripts/backend/fixtures/orchestrator-utterances.json`, the user's own words, average 148 characters, longest 788) break down as:

| verb | count | selector | count |
| --- | --- | --- | --- |
| start (open a pane and/or give it work) | 37 | last_action ("that prompt", "what I asked") | 19 |
| verify ("did you enter that prompt?") | 15 | provider ("the codex terminal") | 17 |
| follow_up ("tell it to also…") | 10 | idle / empty ("one that's not doing anything") | 19 |
| ask (a question to Lina) | 9 | new ("another codex terminal") | 11 |
| open (a pane, no work) | 8 | last_target ("the one you just prompted", "it") | 9 |
| status / results | 14 | done / working / needs_me (by state) | 11 |
| redo / cancel / close / interrupt | 18 | title / topic (by what it is on) | 9 |
| watch / inspect / resume / other | 17 | just_opened / all / none / other | 33 |

Every selector in the right-hand column is a fact about the workspace, not a fact the Brain has to reason out: which pane is free, which one Lina just opened, which one she typed into last, which ones are done, which one carries these words. Run offline against today's code with the projects and launchers the corpus names, only 23 of the 128 are handled without a model call (9 compiled, 14 answered from memory); 105 go to the Brain, 56 of them because the compiler has no shape for the sentence, 24 because the verb is on its blocked list (close, stop, cancel, follow-ups), 14 and 10 because a provider or project is not named in the sentence (at run time the conversation supplies them, so the true number is lower). On the ladder, where the sentences are the corpus's tiers 1 to 4, 17 of 37 requests never reached a model. The target is the other way round: the model reads a sentence only when it carries free-form work to be phrased, never to find out which pane.

What each selector needs from a representation, in words a person would use:

- **free / empty / not doing anything**: a pane whose state is idle and that no task owns.
- **new / another**: no pane; a handle for the one about to be opened, so the next sentence can say "it".
- **just opened / the one you just created**: the handle Lina opened most recently, in this project.
- **the one you just prompted / it / that terminal**: the handle of the latest delivery, and only while that delivery is the latest thing that happened.
- **the other one**: the one other handle in the project beside the latest delivery, or a question.
- **done / working / needs me**: a filter on one state field.
- **the codex terminal**: a filter on provider, then the free one, then a question.
- **the terminal working on X / the X terminal**: a match on what the pane is on (its task text), not on a title the app happened to set.
- **that prompt / what I asked / did you put it in**: the latest delivery's text and outcome.

### 3.2 Seven ways to say what a pane is doing

`turnState` (unknown, idle, running, response, interrupted, waiting, completed) from the runtime; coarse `status` (starting, running, busy, waiting, paused, closed, exited, failed); `processState`, `agentProcessState`, `launchState`; `observation` (observed, provisional, unavailable); `PANE_READINESS_REASONS` (nine values) and `PANE_STATES` (six) from `paneReadiness`; the roster's words (free, working, needs-input, done, starting, stopped); the delivery classifier's seven values; the session summary's `readiness` (ready, starting, unverified) derived separately; the ledger's nine outcomes; the task's nine statuses. A pane that Claude Code has finished is `turnState: response`, `observation: provisional`, `childActivity: true` with `coarseChildObservation: provisional`, `PANE_STATES: done`, roster `done`, and, until this morning, "not a completed turn" to the result reader and the work history. That is finding 17 of the ladder document, and it is the vocabulary problem in one pane.

### 3.3 What the Brain is shown and asked

The interpretation call shows the Brain a roster row per pane (id, name, title, provider, roster state, objective, last prompt time, last result summary; `paneMemory.roster` :154) and the recent ledger, and asks it to return `targetIds`, `kindOfSession`, `assignmentMode` (new, existing, auto), `targetAvailability` (any, idle) and `selection` (one, all). The Brain therefore both picks panes and describes how it picked them, and the review then decides whether to believe it. The operator loop shows a different, larger session summary per pane (`orchestratorContext.sessionSummary` :7: twenty fields including generation, launch token, turn ids, capabilities) and asks the Brain to read screens and act through eight tools. Two views of the same panes, neither the one the user sees.

### 3.4 Tasks, lanes and the operator loop

A task goes `queued → routing → running → waiting-results → finished | failed | cancelled | paused | continued`, or `needs-answer` when a question is asked (`orchestratorTasks.cjs` :55, :144). Each job holds lanes keyed `terminal:<pane>` and `workspace:<worktree identity>` (`orchestrator.cjs` :1972–1983, appended at first authorized submission :988–996). A lane is held while a wait is delivered and not done (`hasWorkspaceOccupancy` :63), so it is released when the pane's turn ends, not when the request's loop ends; that is why "prompt the empty codex terminal" waited four minutes behind a pane whose stub turn never ended, and why the `parallel` flag (:983, set from the sentence's selector) was needed to let a free pane's work through. `conflictingLane` :172–190 is the entire admission predicate; `blockingReason` :211–235 turns it into prose; 99 places in the backend refer to lane internals. Work items are a persisted, authority-free affinity store (`orchestratorWorkItems.cjs`, 85 lines); live reservations live in `orchestratorRouting.cjs` :26–28. Four test files pin the ownership contract with 78 tests (`orchestrator-tasks` 34, `orchestrator-auto-routing-integration` 26, `orchestrator-background-completion-integration` 10, `orchestrator-routing-scheduler` 8): creation is never delivery; a workspace wait does not hold the terminal control lane; an incumbent may take a compatible continuation past a queued mutation; new work in a free or fresh pane runs beside other work and automatic reuse does not; cancelled or failed *submitted* work keeps ownership; result attribution is turn-exact; drafts and plain-shell sends prove nothing.

The operator loop offers the Brain seven operator tools, thirteen read tools, three inspection tools and three memory tools, scoped per grant (`orchestratorToolSchema.cjs` :67–121). Every action passes nine gates in `orchestratorWorkspaceExecutor.cjs` :320–420: grant authority, routing binding, replay key, a step cap of 128 per grant and pane, the uncertain-state latch, lifecycle and pid checks, the observation token (a read from a strictly earlier round, unused, under 30 s: `orchestratorOperator.cjs` :59–68), the input-surface fence in the host (`ptyHost.cjs` :634–671), and, for sends and answers, an app-taken read when the model has none (:325–350). One completion per loop round, up to six tool calls per round, a turn limit of 32 when operating and 12 otherwise (`orchestrator.cjs` :104, :2102), a stagnation detector at six rounds, two executors at once. The loop ends when every target has a `finish_terminal`, when the plan produced a response or a question, or at the turn limit; an inspection's finish is additionally judged by a goal-review model call (`orchestratorGoalReview.cjs`, 20 s). After a wait ends, a result detail re-reads the pane and makes one summary call (1,200 tokens), a progress detail makes another; the summary is then the *only* source of the pane's recorded result (`orchestrator.cjs` :484–526), although `fallbackResultSummary`, `taskWaitSentence` and `collectTaskReports` already produce prose from the same evidence without a model.

What already runs without a model, and proves the direction: the compiler returns the same planner calls the Brain would (`orchestratorCommandCompiler.cjs` :3–23); `canExecuteDirect` (`orchestratorFastPath.cjs` :10) dispatches every direct grant at model round zero; `dispatcher.run` (`orchestratorDispatcher.cjs` :139) performs read, send, post-read and finish in code; `completedOperatorResponse` composes the reply; the submit retry replaces what used to cost a model call (`orchestratorIntegration.cjs` :432–441). On round eighteen these paths carried 31 of 37 requests with at most one model call.

## 4. The overhaul

### 4.1 One terminal model

One object per pane, built by the app from the runtime session and its own records, rebuilt on every inventory change, and shown identically to the user (the sidebar and the Orchestrator dashboard), to the Brain (as the only pane description it ever gets) and to the app's own resolver:

```
{ handle: "T3",                       // stable for the pane's life; the user can say it
  project: "vibeTerminal", provider: "codex",
  state: "idle" | "starting" | "working" | "waiting" | "done" | "stopped",
  on: "Fix the full screen bug",      // the task text: work item objective, else last prompt, else nothing
  owner: "lina" | "user" | null,      // a Lina task, the user by hand, nobody
  lastTouched: { by: "lina", at, what: "prompt" | "interrupt" | "answer" | "opened" },
  result: "…" | null,                 // last recorded result, when the pane is done
  needs: "answer" | "approval" | null }
```

Everything in section 3.1 collapses into fields of this object, computed once: `lastTouched` replaces the four "last pane" computations and the two "just opened" ones; `state` replaces the seven vocabularies for every consumer above the runtime; `on` and `handle` replace the five naming functions; `owner` replaces the three ownership helpers. The runtime keeps its own fine-grained state; the model is the one translation of it, in `paneReadiness`, which already exists and already feeds most consumers.

### 4.2 One reference resolver, before any model

A single function turns a normalized sentence plus the terminal model into a reference: `{ handles: [...], how: "free" | "new" | "just-opened" | "latest" | "other" | "state" | "provider" | "on" | "handle" | "none", question?: "…" }`. It is the resolver's `extractSelector` plus the rules of `resolveAssignment`, `decideTargets`, `resolveLastWorkedTargets`, `stopOfLastWorkedPane`, the pronoun rule and the freshness rule, written once against the model's fields and called once per request. It asks a question when, and only when, the sentence is ambiguous against the model (two free panes and "the one", "the other one" with no latest delivery, "both done" when three are), with the candidates' handles in the question. The compiler, the review, the memory answers and the assignment all take its output; none of them extracts a selector again.

### 4.3 The pipeline

1. Normalize the sentence; build the terminal model.
2. Resolve the reference (4.2). If the sentence is a question about the workspace ("which one needs me", "what did it say", "did you put that in"), answer from the model and the ledger: no model call.
3. If the sentence is a command the compiler recognizes (open, start, follow up, stop, close, cancel, answer, redo), execute it against the resolved handles: no model call. The compiler's blocked-verb list goes away; those verbs become shapes over handles, because the danger they guarded against (the model choosing which pane to stop) no longer exists.
4. Otherwise, one interpretation call whose input is the sentence, the resolved handles and the terminal model, and whose output is the operation and the task text. The Brain no longer returns `targetIds`, `assignmentMode` or `targetAvailability`; it returns handles it was given, or nothing. The target review becomes a one-line check that the returned handles are among the resolved ones.
5. Execute in code: type, verify, report, as the compiled path already does for 14 of 20 Brain turns today.
6. The operator loop stays, for what only a screen can decide (a question form, a menu, an inspection the records cannot answer), with two changes: a refusal the app has already stated ends the loop for that pane instead of being retried, and the per-step request carries a delta of the screen and the tool list once, not 62 KB every step.
7. After a task ends, the result is the pane's recorded excerpt; the spoken summary call becomes optional and off by default on the ladder.

### 4.4 Lanes and ownership

Ownership becomes a field on the terminal model (`owner`, `lastTouched`) and the lane keys become handles. A task owns a handle, not a worktree: two handles in one project run side by side, which is how the user works, and the same handle serializes on its terminal lane exactly as today. The workspace lane survives only for what it was for: an explicit result dependency ("review it, then fix the findings") and the same work item's pending delivery. The `parallel` flag, the selector-keyed exception, `ownsWorkspace` and the incumbent-continuation rule go with it, because the case they distinguish (automatic reuse versus a named free pane) no longer exists once the reference resolver has picked a handle before admission. Of the 78 ownership tests, the ones about creation, drafts, attribution and cancelled-work ownership stand unchanged; the ones about worktree serialization (about 20) are rewritten to the handle contract in one pass, which is the product decision in section 7 made once instead of by exceptions.

### 4.5 The Brain's job after the overhaul

Phrase work. Given "use the empty codex terminal to investigate why the orchestrator reads the whole result out loud", the app has already picked T3; the Brain writes the prompt T3 receives and decides nothing else. Given "there's a terminal that's done, what's the result?", the Brain is not called. Given "tell it to continue", the app knows "it" and either answers the pending question or says it cannot. The model's size matters for the quality of the prompt it writes and for the screen-driven loops, and for nothing else; that is where a cheaper or faster model becomes usable, and why none of them was usable before.

## 6. Migration, with the ladder as the gate

Each phase ends with `npm run test:orchestrator` green and a ladder run on tiers 1 to 4 with no regression against round thirteen (33 of 35, two allowed questions, no harm), run alone on the machine.

1. **The model.** Add `terminalModel(sessions, records)` beside `paneReadiness`, with handles persisted per pane. Feed the user-facing surfaces (dashboard, sidebar labels) and the memory answers from it. Delete the memory module's own naming. Tests: one fixture of real inventories per state.
2. **The reference resolver.** Write it against the model; make `extractSelector`, the review's bases, `resolveLastWorkedTargets`, the pronoun and freshness rules and `actionHistory` delegate to it, then delete them. Rewrite the resolver, review and fences tests (about 80) to the reference contract, one case per corpus selector. This is the phase that changes behaviour least and code most.
3. **Handles to the Brain.** The interpretation call shows the model and asks for handles; the schema loses `targetIds`, `assignmentMode`, `targetAvailability`, `selection`. The review becomes the handle check. Ladder tier 2 and 4 are the proof.
4. **Compiler over handles.** Remove the blocked-verb list; add shapes for stop, close, cancel, answer, follow-up and redo over resolved handles. Zero-model coverage of the 128 goes from 23 to a number this phase reports.
5. **Execution trim.** Refusal short-circuit; tool list sent once; screen deltas; result excerpt without a summary call. Measured by calls per turn and bytes per call on the ladder.
6. **Ownership by handle.** The lane change from section 4.4, with the 26 ownership tests rewritten to the handle contract in one pass rather than the one-line exceptions of 2026-09-15.

## 7. Decisions the user owns

- Two Lina tasks in one project run side by side by default (the corpus assumes it; today's rule serializes unless the sentence named an empty or new pane).
- "The other one" right after a question is a question, not a guess.
- Handles are visible in the UI and the Brain's replies say them ("I put it in T3").
- A finished pane's spoken result is the recorded excerpt, not a model summary, unless the user asks for a summary.
- Which of the eighteen ladder-round fixes stay as-is through the migration: all of them, until the phase that subsumes each one deletes it.

## 8. Risks

- The 1,477 pinned tests encode today's split; phases 2 and 6 rewrite about 300 of them, and every rewrite is a chance to lose a guarantee. The ladder is the second net and must run after every phase.
- Handles that change when a pane is closed and reopened break "T3" in the user's mouth; handles must be assigned per pane life and never reused within a session.
- The runtime's own states are not touched; if the model's `state` is wrong, it is wrong once, visibly, in one place, which is the point.
