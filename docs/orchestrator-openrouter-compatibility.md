# OpenRouter model compatibility investigation

Investigated September 8, 2026 (Toronto time; September 9 UTC).

## Finding

The strongest reproduced cause is the interpreter's forced, named tool choice.
The same full interpreter prompt and tool schema completed quickly on Mercury
and GLM when `tool_choice` changed to `auto`. Their forced requests did not
complete within a separate 90-second diagnostic deadline. Merely increasing
Lina's original 45-second deadline would therefore not resolve these examples.

Gemini returned HTTP 400 for the forced request. The old compatibility handler
then changed tool choice to `auto`, and remembered that downgrade. Mercury and
GLM returned HTTP 200 headers and continued sending response bytes without
finishing the JSON body, so they never reached that HTTP-400/422 fallback.
This explains the observed asymmetry: the model that rejected the request
quickly recovered, while the models that accepted it hit Lina's local deadline.

This establishes a reproducible request-compatibility problem. It does not
identify the internal provider implementation defect or prove that every
possible timeout has the same cause. GLM's underlying provider can vary between
requests; Mercury's successful responses identified Inception. Provider
congestion and rate limits remain separate failure modes.

## Controlled live comparison

The diagnostic requests used the actual exported `INTENT_SYSTEM` and
`INTENT_TOOL`, a synthetic instruction asking how many terminals were open,
and an empty synthetic workspace. They used the selected model, temperature
zero, reasoning effort low, a 4,000-token output cap, and nonstreaming JSON.
Within each full-prompt comparison the deliberate change was named tool
choice versus `auto`; the full schema and system instructions were retained.
These were representative requests, not a replay of private user instructions.

| Model | Simple text control | Full schema, forced named choice | Full schema, automatic choice |
| --- | --- | --- | --- |
| Mercury 2.5 | 692 ms | Aborted at 90,012 ms; HTTP 200 headers at 363 ms | 947 ms and 912 ms; valid tool calls |
| GLM 5.3 Flash | 1,578 ms | Aborted at 90,012 ms; HTTP 200 headers at 1,341 ms | 5,762 ms and 8,350 ms; valid tool calls |
| Gemini 3.8 Flash | Not needed | HTTP 400 after 962 ms | 2,200 ms; valid tool call |
| Nemotron 3.5 Lightning | Not tested | Not tested in this comparison | First HTTP 429; later valid tool call in 10,401 ms |

Nemotron's initial error identified DeepInfra's shared upstream pool as
temporarily rate limited. A later automatic-choice request succeeded. That
failure should remain classified as upstream rate limiting, rather than be
attributed to the named-choice timeout mechanism.

## Source changes

1. **Automatic tool selection from the first interpreter call.** The configured
   Brain model stays the same. `auto` controls tool selection, not model routing.
   The interpreter still requires exactly one `interpret_workspace` call,
   valid JSON, operation-specific fields, and normalized authorization. Text
   alone cannot authorize a terminal action. Malformed output retains the
   existing bounded repair and fails closed if still invalid. The full schema
   and system prompt remain intact.
2. **Capability-aware completion options.** All Brain call paths use a shared
   helper. Initial output reservations honor the advertised completion maximum;
   exhausted responses do not receive an identical-budget widening attempt.
   Temperature is sent only when advertised. Reasoning effort follows explicit
   supported efforts, preferring low; absent effort metadata retains the prior
   low-effort behavior. Optional reasoning is not silently disabled.
3. **Local readiness check.** A known model context window must fit the fixed
   production interpreter before readiness succeeds. In the tested schema,
   minimal requests fail locally for 8k, 16k and 32k windows and fit at 64k.
   The system text is 19,674 UTF-8 bytes and the schema 10,897 bytes. Lina's
   conservative context accounting uses serialized bytes, not a tokenizer
   count. Readiness still checks credentials, catalog presence and fixed local
   fit; it does not claim a successful live generation.
4. **Useful timing diagnostics.** Model stages now distinguish response headers
   from complete JSON parsing, record effective tool choice and deadline, and
   retain bounded provider/generation identity and usage counts on success.
   Failure metadata distinguishes `client-deadline` from `upstream-timeout`
   and identifies whether failure occurred while waiting for headers or body.
   Response text, reasoning, tool arguments and raw provider error bodies are
   excluded from the application's diagnostic log.

Relevant files: `backend/orchestrator.cjs`,
`backend/orchestratorModelOptions.cjs`, `backend/openRouterErrors.cjs`, and
`backend/orchestratorDiagnostics.cjs`.

The 45-second total JSON deadline remains in place. There is no newly added
timeout retry, model substitution, provider pinning or replay of terminal
actions. A legitimately slow provider can still exceed that deadline.
Streaming with separate progress and overall deadlines is a potential follow-up,
but it was not needed to fix the reproduced named-choice incompatibility.

This checkout's source changes do not replace the running installed archive.
The installed 0.1.103 application needs a newly packaged build to receive them.
The package version alone cannot establish whether a running process contains
this change; inspect the archive or its request diagnostics.

## External protocol references

OpenRouter documents automatic and forced tool selection and keeps client-side
execution separate from model suggestions. That is why automatic selection can
retain Lina's application-level validation and authorization.
[Tool calling](https://openrouter.ai/docs/guides/features/tool-calling)

The catalog exposes model-specific supported reasoning efforts and mandatory
reasoning metadata. Those fields inform completion options rather than assuming
that every model accepts the same effort.
[Reasoning metadata](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)

Upstream status errors and streaming errors have different response envelopes;
provider rate limiting is distinct from a client abort. Provider fallback can
also add latency. These are possible additional causes, not substitutes for the
controlled request comparison above.
[Error handling](https://openrouter.ai/docs/api_reference/errors-and-debugging),
[latency](https://openrouter.ai/docs/guides/best-practices/latency-and-performance)
